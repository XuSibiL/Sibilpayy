# ۱۳ — یک پورت برای API و درگاه

آدرسی که API روی آن است و آدرسی که صفحه پرداخت روی آن است باید یک پورت داشته باشند: یک میزبان، یک پورت، https.

## ۱) چرا

هر چیزی که به این سیستم وصل می‌شود، یعنی سایت و ربات و اپ و افزونه فروش، فقط یک آدرس می‌شناسد. وقتی این آدرس با آدرس صفحه پرداخت یکی نباشد این‌ها می‌شکنند:

| مشکل | چطور خودش را نشان می‌دهد |
|---|---|
| کوکی و سشن صفحه پرداخت | خریدار لینک را باز می‌کند و پیام «فاکتور پیدا نشد» می‌بیند |
| ریدایرکت https | درخواست از یک پورت می‌آید و به پورت دیگر پرتاب می‌شود و ربات پاسخی نمی‌گیرد |
| افزونه‌های آماده | یک base هاردکد دارند و لینک برگشتی روی پورت دیگر را معتبر نمی‌دانند |
| webhook و callback | آدرس ثبت‌شده در درگاه‌های دیگر مثل کارت و کریپتو پورت قدیمی را دارد |

نتیجه عملی همین وضعیت، پیامی است که در ربات‌های فروش دیده می‌شود: «نتیجه ساخت این فاکتور هنوز مشخص نیست». یعنی درخواست رفت و پاسخی برنگشت و از بیرون هم نمی‌شود فهمید فاکتور ساخته شد یا نه.

## ۲) هر لینک از کدام تنظیم ساخته می‌شود

| لینک | تنظیم | پیش‌فرض |
|---|---|---|
| API و سایت و مستندات و APK و ریدایرکت‌ها | `BASE_URL` | — |
| صفحه پرداخت `/{…}/pay/…` و `payment_url` در پاسخ API | `PAYMENT_BASE_URL` | همان `BASE_URL` |
| مینی‌اپ (`/mini`) | `MINI_BASE_URL` | همان میزبان، بدون پورت یعنی ۴۴۳ |

مینی‌اپ تنها استثناست، چون تلگرام در URL وب‌اپ پورت نمی‌پذیرد و برای همین روی ۴۴۳ سرو می‌شود. بقیه لینک‌ها باید یک پورت باشند.

## ۳) قاعده یک پورت در کد

از نسخه 1.5.9.22:

- اگر `PAYMENT_BASE_URL` پورت دیگری بدهد نادیده گرفته می‌شود و همه لینک‌ها از پورت `BASE_URL` ساخته می‌شوند.
- در لاگ یک هشدار ثبت می‌شود:

```
PORT-ONE-V1: پورتِ لینکِ پرداخت (8443) با پورتِ API (2053) یکی نیست؛
             لینک‌ها از پورتِ API ساخته می‌شوند
```

- همین قاعده در ربات هم اعمال می‌شود، در `bot/config.py` با نام `PORT_MISMATCH`، و فرمان `/diag` خط «پورت درگاه» را نشان می‌دهد: یکی یا جدا.

اگر واقعا می‌خواهی عمدا جدا باشند، که توصیه نمی‌شود، در `.env` این را بگذار:

```
STRICT_ONE_PORT=false
```

## ۴) پیکربندی درست در سه خط

```env
BASE_URL=https://pay.example.com
PAYMENT_BASE_URL=https://pay.example.com
MINI_BASE_URL=https://pay.example.com
```

اگر پورت صریح می‌گذاری، پورت باید همان پورتی باشد که مسیر `/api/v1/` را واقعا سرو می‌کند، نه پورتی که فقط صفحه پرداخت را می‌شناسد.

`MINI_BASE_URL` عمدا بدون پورت است، یعنی ۴۴۳.

## ۵) بررسی سریع

معیار، مسیر API است نه `/health`:

```bash
curl -s -o /dev/null -w "%{http_code}\n" https://pay.example.com/api/v1/invoices/by-order/probe
```

- `401` یا `404` با کلید یعنی مسیر API مستقیم جواب می‌دهد و همین آدرس درست است.
- `302` یا `301` یعنی این آدرس به API نمی‌رسد و پراکسی یا وب‌سرور ریدایرکت می‌کند.
- `000` یا `502` یعنی سرویس روی آن آدرس گوش نمی‌دهد.

`200` روی `/health` به‌تنهایی هیچ‌چیز را ثابت نمی‌کند، چون یک پراکسی می‌تواند فقط `/health` را به برنامه بفرستد و بقیه مسیرها را ریدایرکت کند؛ بند ۶ همین است.

آدرس را قبل از باز کردن مسیر API عوض نکن، وگرنه ربات و سایت با هم می‌خوابند.

از داخل سرور می‌توانی مقدار نهایی را ببینی، نه فقط `.env` را:

```bash
cd /opt/sibilpay && ./venv/bin/python -c "import sys;sys.path.insert(0,'backend');from app.config import settings,payment_base;print(settings.base_url);print(payment_base());print(settings.mini_base)"
```

`BASE_URL` و `PAYMENT_BASE` باید یکی باشند.

## ۶) اگر `302` گرفتی

`302` یا `301` با هدر `Location` یعنی درخواست به API نرسیده و یک لایه دیگر، مثل وب‌سرور یا پراکسی، آن را به پورت دیگر پرتاب کرده است.

```bash
curl -sS -o /dev/null -D - https://pay.example.com/api/v1/invoices/by-order/probe | head -5
```

```
HTTP/2 302
location: https://pay.example.com/api/v1/invoices/by-order/probe   ← یعنی ۴۴۳
server: Caddy
```

مارک `server:` منبع را لو می‌دهد:

| `server:` | یعنی پاسخ از کجاست |
|---|---|
| `Caddy` یا `nginx` | پراکسی یا وب‌سرور ریدایرکت می‌کند و کد برنامه دخیل نیست |
| `uvicorn` | پاسخ از خود برنامه سیبیل‌پی است |

### دام `/health`

`200` روی `/health` سلامت مسیر API را ثابت نمی‌کند. یک پراکسی می‌تواند فقط `/health` را به برنامه بفرستد و بقیه مسیرها را ریدایرکت کند و نتیجه این می‌شود:

```
https://HOST:PORT/health          → 200  (uvicorn)
https://HOST:PORT/api/v1/…        → 302  (پروکسی → ۴۴۳)
```

یعنی آن پورت زنده است ولی API روی آن نیست. آدرس درست همان پورتی است که `/api/v1/…` رویش JSON می‌دهد.

### آزمون پذیرش

| درخواست | پاسخ درست | پاسخ غلط |
|---|---|---|
| `/api/v1/invoices/by-order/probe` بدون کلید | `401` و JSON | `302` و `Location` |
| همان مسیر با کلید معتبر و `order_id` ناموجود | `404` و `INVOICE_NOT_FOUND` | `302` یا HTML |
| همان مسیر با کلید معتبر و فاکتور موجود | `200` و JSON فاکتور | `302` |

هیچ کلاینتی نباید ریدایرکت را خودکار دنبال کند. با فعال بودن follow ممکن است یک `POST` به `GET` تبدیل شود و فاکتور ساخته نشود، در حالی که گزارش می‌گوید نتیجه نامشخص.

## ۷) چک‌لیست

- [ ] `BASE_URL` و `PAYMENT_BASE_URL` پورت یکسان دارند.
- [ ] `https://HOST/api/v1/…` از بیرون JSON می‌دهد، یعنی `401` بدون کلید، نه `302`.
- [ ] `https://HOST/health` از بیرون `200` می‌دهد.
- [ ] `MINI_BASE_URL` روی ۴۴۳ است و پورت ندارد.
- [ ] در ربات، `/diag` می‌گوید پورت درگاه یکی است.
- [ ] آدرس webhook و callback درگاه‌های دیگر مثل کارت و کریپتو هم به همان پورت اشاره می‌کند.

## پورت فعلی

پورت فعلی فقط ۴۴۳ است. هیچ آدرسی با `:2053` یا `:19055` در نصب تازه استفاده نمی‌شود و آن‌ها فقط در بندهای تاریخی یا مثال آمده‌اند. آدرس درست `https://pay.example.ir/…` بدون پورت است و `BASE_URL` هم همان است.

## پشت رله، مثل بک‌پک یا پروکسی: صفحه سفید نده

اگر دامنه به یک سرور ایرانی اشاره کند و آن سرور ترافیک ۴۴۳ را به سرور اصلی، مثلا فرانسه، رد کند، دو حالت دارد:

| حالت رله | چه می‌شود | تنظیم درست |
|---|---|---|
| TCP passthrough که TLS در سرور اصلی تمام می‌شود | همه‌چیز درست است | توصیه‌شده |
| رله TLS را خودش تمام می‌کند و HTTP ساده به سرور اصلی می‌فرستد | چون `FORCE_HTTPS` روشن است هر درخواست `308` به https می‌خورد و همان مسیر دوباره از رله برمی‌گردد، پس حلقه می‌شود و مرورگر صفحه سفید نشان می‌دهد | رله باید `X-Forwarded-Proto: https` بفرستد یا آدرسش در `TRUSTED_PROXIES` باشد |

```env
# .env روی سرورِ اصلی
TRUSTED_PROXIES=185.243.49.77
```

از 1.5.9.27 این مقدار پیش‌فرض همان رله است و برای رله دیگر خودت پُرش کن. با این کار درخواستی که از رله می‌آید https فرض می‌شود و صفحه سفید تمام می‌شود.

### چطور در سه ثانیه بفهمی حلقه است

```bash
curl -s -o /dev/null -w "%{http_code}\n" -H "Host: pay.example.ir" http://127.0.0.1:8000/docs   # پورتِ داخلیِ خودِ API
```

- `200` یعنی مسیر سالم است.
- `308` یعنی همان حلقه؛ رله هدر نمی‌فرستد یا در `TRUSTED_PROXIES` نیست.

### `/health` روی ۴۴۳ هم باید باز باشد

روی ۴۴۳ فقط فهرست مشخصی از مسیرها به اپ می‌رود: `/pay/… /g/… /@… /api/… /static/… /docs`. اگر `/health` در آن فهرست نباشد به پورت پرداخت یعنی ۲۰۵۳ ریدایرکت می‌شود و پشت رله‌ای که فقط ۴۴۳ را رد می‌کند باز نمی‌شود. با `install/update-1.5.9.28.sh` هم اضافه می‌شود، هم در Caddy و هم در nginx، با بکاپ و بازگشت خودکار.

```bash
curl -sk -o /dev/null -w "%{http_code}\n" --resolve pay.example.ir:443:127.0.0.1 https://pay.example.ir/health
```

`200` یعنی درست و `308` یعنی هنوز به پورت دیگر می‌رود.
