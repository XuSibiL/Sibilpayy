# ۱۰ — تلاش ناموفق، نتیجه نامشخص و idempotency

این سند می‌گوید سمت فروشگاه یا ربات چه چیزی لازم است و API سیبیل‌پی چه چیزی را تضمین می‌کند. هر دو طرف باید همین رفتار را پیاده کنند.

## مسئله

در تماس با API این حالت پیش می‌آید:

```
ربات → POST /api/v1/invoices  →  …  →  پاسخ هرگز به ربات نمی‌رسد
```

نتیجه یکی از این دو است و از بیرون قابل تفکیک نیست:

| حالت | یعنی |
|---|---|
| شکست قطعی | درخواست رد شد و هیچ فاکتوری ساخته نشد |
| نتیجه نامشخص | ممکن است فاکتور ساخته شده باشد ولی پاسخ گم شده باشد |

اگر این دو را یکی بگیری دو اتفاق بد می‌افتد: یا فاکتور تکراری ساخته می‌شود، یا رکورد در وضعیت «نیازمند بررسی» قفل می‌شود و تلاش‌های بعدی همان کاربر هم قبل از رسیدن به درگاه متوقف می‌شود.

## شکست قطعی

این کدها تضمین می‌کنند فاکتوری ساخته نشده، پس می‌توانی همان لحظه پیام مناسب نشان بدهی و اجازه تلاش دوباره بدهی:

| کد | معنا |
|---|---|
| `INVALID_TOKEN` یا `KEY_DISABLED` | کلید نادرست یا غیرفعال؛ فاکتوری ساخته نشد |
| `INVALID_AMOUNT` | مبلغ صفر یا منفی یا بیش از سقف |
| `UNKNOWN_GATEWAY` یا `GATEWAY_DISABLED` | درگاه خواسته‌شده برای این فروشگاه فعال نیست |
| `NO_CARD_AVAILABLE` | فروشگاه کارت فعال واریز ندارد |
| `WALLET_INSUFFICIENT` | کیف پول کارمزد فروشگاه کافی نیست؛ تقصیر خریدار نیست |
| `AMOUNT_POOL_EXHAUSTED` | همه مبلغ‌های یکتا برای کارت‌های این فروشگاه پر است |
| `TOPUP_TOO_SMALL` | شارژ کیف پول کمتر از حد مجاز است |

هر پاسخ 4xx با `success: false` در همین دسته است، به‌جز استثنای بخش بعد. کد `DUPLICATE` نداریم؛ idempotency با `order_id` کار می‌کند.

## نتیجه نامشخص

اگر پاسخ را ندیدی، یعنی timeout یا قطع اتصال یا خطای 5xx یا پاسخ ناقص، فرض نکن فاکتور ساخته نشده. اول استعلام بگیر. این مسیر دقیقا برای همین حالت هست:

```http
GET /api/v1/invoices/by-order/{order_id}
Authorization: Bearer sibil_pay_live_…
```

| نتیجه | معنا | کار درست |
|---|---|---|
| `200` با فاکتور | آن درخواست موفق بوده | همان لینک پرداخت را به کاربر بده |
| `404` با `INVOICE_NOT_FOUND` | مطمئنی فاکتوری ساخته نشده | با خیال راحت دوباره درخواست بفرست |

## idempotency با `order_id`

`order_id` شناسه سفارش خود فروشگاه است، یک رشته تا ۱۲۰ کاراکتر.

- اگر برای همین فروشگاه و همین `order_id` فاکتوری با وضعیت `pending`، `partially_paid` یا `paid` وجود داشته باشد، `POST /api/v1/invoices` فاکتور تازه نمی‌سازد و همان را با `200` و `"idempotent_replay": true` برمی‌گرداند.
- اگر آن فاکتور `expired` یا `cancelled` باشد، درخواست تازه فاکتور جدید می‌سازد و `201` با `"idempotent_replay": false` می‌دهد.

پس این دو درخواست یک نتیجه دارند:

```bash
# تلاشِ اول — پاسخ گم شد
curl -X POST $SERVER/api/v1/invoices -H "Authorization: Bearer $KEY" \
  -H 'Content-Type: application/json' \
  -d '{"amount_rial": 500000, "order_id": "order-8f21c"}'

# تلاشِ دوم با همان order_id — فاکتورِ تکراری ساخته نمی‌شود
curl -X POST $SERVER/api/v1/invoices -H "Authorization: Bearer $KEY" \
  -H 'Content-Type: application/json' \
  -d '{"amount_rial": 500000, "order_id": "order-8f21c"}'
```

دامنه یکتایی `order_id` همان فروشگاه است، نه کل سامانه. دو فروشگاه مختلف می‌توانند `order-1` داشته باشند.

## الگوریتم پیشنهادی برای ربات و سایت

```text
۱. order_id یکتا برای این تلاش بساز (مثلاً order-<uuid>) و در دیتابیسِ خودت
   با وضعیت «creating» ثبتش کن.
۲. POST /api/v1/invoices با همان order_id بفرست.
   ├─ 2xx  → «created»؛ شناسه و لینک را ذخیره کن. تمام.
   ├─ 4xx با کدِ جدولِ بندِ ۱ → «rejected»؛ پیامِ فارسی به کاربر نشان بده
   │        و همان order_id را باطل کن (تلاشِ بعدی، order_id تازه بگیرد).
   └─ timeout / 5xx / پاسخِ ناقص → «unknown»؛ **قفل نکن**، فقط برو مرحلهٔ ۳.
۳. با همان order_id استعلام بگیر:
   GET /api/v1/invoices/by-order/{order_id}
   ├─ 200 → «created» (از فاکتورِ برگشتی استفاده کن)
   └─ 404 → «rejected»؛ اجازهٔ تلاشِ دوباره بده (همان order_id هم بی‌خطر است)
۴. اگر استعلام هم ناموفق بود (شبکه قطع است): وضعیت را «unknown» نگه دار،
   ولی *مسدودکنندهٔ دائمی* نساز — با یک بازهٔ زمانی (مثلاً ۲ دقیقه) دوباره
   استعلام بزن. تا تعیین‌تکلیف نشدن، فاکتورِ تکراری برای همان کاربر نساز.
```

## چیزهایی که نباید انجام شود

1. مسدود کردن همیشگی کاربر به‌خاطر یک تلاش نامشخص. نامشخص با ناموفق فرق دارد.
2. حذف سابقه یا پرداخت‌شده اعلام کردن یا لغو فرضی برای رفع انسداد. رفع انسداد فقط با استعلام و تعیین وضعیت انجام می‌شود.
3. فرستادن درخواست تکراری بدون `order_id` وقتی فاکتور قبلی همان کاربر هنوز باز است. با `order_id` این حالت پیش نمی‌آید.
4. نشان دادن کد داخلی ربات به مشتری. پیام مشتری باید فارسی و قابل‌فهم باشد و یک شناسه پیگیری مثل `order_id` داشته باشد؛ کدهای فنی فقط در گزارش مدیریتی و بدون اطلاعات محرمانه ثبت شوند.

## رفتار درگاه در حالت تکراری

| درخواست | پاسخ |
|---|---|
| `POST /invoices` با `order_id` تازه | `201` و `idempotent_replay: false` |
| `POST /invoices` با `order_id` فاکتور باز | `200` و `idempotent_replay: true` و همان فاکتور |
| `POST /invoices` با `order_id` فاکتور منقضی یا لغوشده | `201` و فاکتور تازه |
| `GET /invoices/by-order/{id}` موجود | `200` با فاکتور |
| `GET /invoices/by-order/{id}` ناموجود | `404` و `INVOICE_NOT_FOUND` |

فاکتور همان لحظه‌ای که `201` برمی‌گردد در دیتابیس ثبت شده است، پس استعلام بعدی حتی چند میلی‌ثانیه بعد آن را می‌بیند.

## گزارش‌های سمت درگاه

- ساخت موفق به تاپیک «فاکتورها» در گروه گزارش‌های اپراتور می‌رود.
- ساخت ردشده به تاپیک «خطاها» می‌رود، همراه با دلیل و مبلغ و نام فروشگاه.

اگر درخواست اصلا به درگاه نرسد، یعنی خطای داخلی ربات پیش از تماس با API، درگاه چیزی برای گزارش ندارد و آن خطا باید در گزارش خود ربات دیده شود.
