# ۰۷ — امنیت

این سند کوتاه است چون فقط چند قاعده ساده لازم دارد.

## کلید API

کلید شکل `sibil_pay_live_…` دارد و کلید تست `sibil_pay_test_…` است.

| درست | غلط |
|---|---|
| در متغیر محیطی سرور (`SIBILPAY_KEY`) | داخل جاوااسکریپت صفحه |
| در کد PHP یا Node یا Python سمت سرور | در اپ موبایل که decompile می‌شود |
| در `.env` که در git نیست | commit شده در گیت‌هاب |
| چرخش کلید پس از لو رفتن | استفاده مشترک بین چند فروشگاه |

اگر کلیدی لو رفت در پنل باطلش کن و کلید تازه بساز. کلید بعد از ساخت فقط یک بار نمایش داده می‌شود.

## webhook

سه چیز همیشه:

1. امضا را بررسی کن: `HMAC_SHA256(secret, "<t>." + raw_body)`
2. کهنگی را بررسی کن: اختلاف `t` بیش از ۵ دقیقه یعنی رد
3. idempotent باش، چون یک رویداد می‌تواند دو بار برسد

مقایسه را با `hash_equals` در PHP یا `crypto.timingSafeEqual` در Node یا `hmac.compare_digest` در Python انجام بده، نه با `==`.

به این‌ها به‌تنهایی اعتماد نکن:

- پارامتر `?status=paid` در URL بازگشت
- بدنه درخواستی که امضا ندارد
- پیامی که کاربر در تلگرام می‌فرستد مثل «واریز کردم»

## گوشی تأیید (اپ Forwarder)

- گوشی پیامک‌های بانک را می‌خواند، پس روی گوشی خود فروشنده نصب شود و قفل صفحه داشته باشد.
- دستگاه با کد اتصال یک‌بارمصرف وصل می‌شود و بعد از اتصال پیامک‌های قدیمی‌تر از زمان اتصال هیچ‌وقت حساب نمی‌شوند. قطع اتصال این مرز را صفر می‌کند.
- اگر گوشی مدتی بی‌شبکه بود، پیامک‌های همان بازه دیرتر می‌رسند ولی همچنان معتبرند، تا وقتی کلید فروشگاه و دستگاه معتبر باشند.
- پیامک‌ها فقط برای تطبیق استفاده می‌شوند؛ رمز کارت و اینترنت‌بانک نباید به هیچ سروری برود.

## داده‌ها

- مبلغ پرداختی با مبلغ دقیق یکتا (`payable_rial`) تطبیق داده می‌شود، نه با نام فرستنده.
- شماره کارت فروشنده برای مشتری فقط به شکل بانک و چهار رقم آخر و نام صاحب کارت نمایش داده می‌شود. شماره کامل در پاسخ‌های عمومی API نمی‌آید.
- اطلاعات کارت خریدار هرگز از او گرفته نمی‌شود، چون پرداخت کارت‌به‌کارت است و مشتری خودش از اپ بانک خودش واریز می‌کند.
