# ۰۷ — امنیت

این سند کوتاه است چون فقط چند قاعدهٔ ساده لازم دارد.

---

## کلیدِ API

کلید شکلِ `sibil_pay_live_…` دارد (کلیدِ تست: `sibil_pay_test_…`).

| ✅ درست | ❌ غلط |
|---|---|
| در متغیرِ محیطی سرور (`SIBILPAY_KEY`) | داخلِ جاوااسکریپتِ صفحه |
| در `php`/`node`/`python` سمتِ سرور | در اپِ موبایلِ قابلِ decompile |
| در `.env` که در git نیست | commit شده در گیت‌هاب |
| چرخش (rotate) پس از لو رفتن | استفادهٔ مشترک بینِ چند فروشگاه |

اگر کلیدی لو رفت: در پنل باطلش کن و کلیدِ تازه بساز. کلید بعد از ساخت فقط یک بار
نمایش داده می‌شود.

---

## وب‌هوک

سه چیز همیشه:

1. **امضا را چک کن** — `HMAC_SHA256(secret, "<t>." + raw_body)`
2. **کهنگی را چک کن** — اختلافِ `t` بیش از ۵ دقیقه = رد
3. **یدمپوتنت باش** — یک رویداد می‌تواند دو بار برسد

با `hash_equals` (PHP) یا `crypto.timingSafeEqual` (Node) یا `hmac.compare_digest`
(Python) مقایسه کن، نه با `==`.

**هرگز** به این‌ها به‌تنهایی اعتماد نکن:
- پارامتر `?status=paid` در URLِ بازگشت
- بدنهٔ درخواستی که امضا ندارد
- پیامِ تلگرامی که کاربر می‌فرستد («واریز کردم!»)

---

## گوشیِ تأیید (اپِ Forwarder)

- گوشی، پیامک‌های بانک را می‌خواند؛ پس روی گوشیِ **خودِ فروشنده** نصب شود، با قفلِ صفحه.
- دستگاه با **کدِ اتصالِ یک‌بارمصرف** وصل می‌شود و بعد از اتصال، پیامک‌های قدیمی
  (قبل از زمانِ اتصال) هیچ‌وقت حساب نمی‌شوند. «قطع اتصال» این مرز را صفر می‌کند.
- اگر گوشی مدتی بی‌شبکه بود، پیامک‌های همان بازه دیرتر می‌رسند ولی همچنان معتبرند —
  تا وقتی که کلیدِ فروشگاه و دستگاه معتبر باشند.
- پیامک‌ها فقط برای تطبیق استفاده می‌شوند؛ رمزِ کارت/اینترنت‌بانک هرگز نباید به
  هیچ سروری برود.

---

## داده‌ها

- مبلغِ پرداختی با **مبلغِ دقیقِ یکتا** (`payable_rial`) تطبیق داده می‌شود، نه با نامِ فرستنده.
- شمارهٔ کارتِ فروشنده برای مشتری فقط به شکلِ «بانک + ۴ رقمِ آخر + نامِ صاحب». شمارهٔ کامل
  در پاسخ‌های عمومی API نمی‌آید.
- اطلاعاتِ کارتِ خریدار هرگز از مشتری گرفته نمی‌شود — پرداخت کارت‌به‌کارت است، خودِ
  مشتری از اپِ بانکِ خودش واریز می‌کند.
