# ۱۲ — چند فاکتور هم‌زمان و دام صف تک‌فاکتوری

هر `POST /api/v1/invoices` یک فاکتور تازه است. سیبیل‌پی صفی ندارد؛ اگر خریدارها پشت سر هم می‌مانند، آن صف را کد فروشگاه ساخته است.

این سند برای کسی است که درگاه را به سایت یا اپ یا ربات یا افزونه آماده وصل می‌کند و می‌خواهد ده‌ها خریدار هم‌زمان، ده‌ها فاکتور مستقل بگیرند.

## ظرفیت

| موضوع | عدد | توضیح |
|---|---|---|
| ساخت فاکتور هم‌زمان | بدون محدودیت عملی | هر درخواست یک `id` و یک لینک پرداخت جدا دارد |
| فاکتور باز با همان مبلغ روی یک کارت | ۹۹۹ | هر فاکتور دنباله ریالی یکتا می‌گیرد: `amount_rial + 1…999` |
| فاکتور باز با مبلغ متفاوت | بدون تداخل | ۵۰۰٬۰۰۰ و ۷۵۰٬۰۰۰ با هم رقابتی ندارند |
| کارت بیشتر | چرخش خودکار | `priority` و حجم روز هر کارت تعیین می‌کند کدام انتخاب شود |
| نرخ درخواست | ۳۰۰ در دقیقه برای هر IP | بیشتر از این `429 RATE_LIMIT_EXCEEDED` |

نتیجه تست داخلی روی همان موتور تخصیص مبلغ:

```
۳۰ فاکتورِ هم‌مبلغ و هم‌زمان: 30 مبلغِ یکتا از 30 → OK
نمونه: 500,214 · 500,236 · 500,320 · 500,337 · 500,339 … 500,996
۹۹۹ فاکتورِ بازِ هم‌مبلغ روی یک کارت: OK
هزارمی: AMOUNT_POOL_EXHAUSTED
مبلغِ متفاوت (۷۵۰٬۰۰۰) هم‌زمان با ۹۹۹ فاکتورِ باز → 750,965 ✔
```

مبلغ‌ها کمی فرق دارند چون پیامک بانکی شناسه پرداخت همراه ندارد و تنها سرنخ قابل اعتماد، مبلغ دقیق است. پس هر فاکتور باز چند ریال بیشتر دارد تا از بقیه تفکیک شود. همیشه `payable_rial` را بگیر و `amount_rial` را گرد نکن.

مبلغ یکتا فقط وقتی تمام می‌شود که واقعا ۹۹۹ فاکتور باز هم‌مبلغ روی یک کارت داشته باشی، که با انقضای پیش‌فرض ۳۰ دقیقه خودبه‌خود آزاد می‌شود.

## تنها حالتی که فاکتور تازه ساخته نمی‌شود

اگر فروشگاه با همان `order_id` دوباره درخواست بدهد و آن فاکتور هنوز `pending` یا `partially_paid` یا `paid` باشد، سیبیل‌پی همان فاکتور قبلی را برمی‌گرداند و `idempotent_replay: true` می‌گذارد:

```json
{ "success": true, "data": { "id": "inv…", "payable_rial": 500214,
  "payment_url": "https://SERVER/pay/…", "status": "pending",
  "idempotent_replay": true } }
```

این عمدی است: اگر پاسخ به فروشگاه نرسیده باشد نباید پول یک سفارش دو بار از مشتری گرفته شود. با `expired` یا `cancelled` این اتفاق نمی‌افتد و فاکتور تازه ساخته می‌شود.

هر تلاش خرید باید `order_id` یکتای خودش را داشته باشد. `order_id` شناسه سفارش است، نه شناسه کاربر.

## دام صف: یک پرداخت معلق برای هر کاربر

این خطای رایج در ربات‌های فروش و افزونه‌های آماده است:

```python
# ❌ اشتباه — یک فاکتور برای همه، و بقیه در صف
if user.pending_payment:
    return "نتیجهٔ درخواست قبلی هنوز مشخص نیست؛ بعداً بررسی کنید"
inv = create_invoice(order_id=f"user-{user.id}")   # و بدتر: order_id ثابت!
```

| کاری که کد فروشگاه می‌کند | نتیجه‌ای که می‌بینی |
|---|---|
| یک `order_id` ثابت برای همه تلاش‌ها (`user-12`) | تا وقتی فاکتور اول باز است همه همان فاکتور و همان لینک را می‌گیرند: یک فاکتور برای همه |
| قفل «تا نتیجه قبلی روشن نشود فاکتور جدید ممنوع» | کاربر پول واریز کرده، پیامک نرسیده یا سایت قطع بوده، و تا ابد منتظر بررسی می‌ماند |
| `pending` را رها می‌کنی و فقط به webhook امیدواری | فاکتور ۳۰ دقیقه بعد `expired` می‌شود ولی کاربر همچنان قفل است |
| مبلغ را گرد می‌کنی (`// 10`، تومان) | مبلغ واریز با `payable_rial` یکی نیست و پرداخت هیچ‌وقت تطبیق نمی‌شود |
| فاکتور جدید فقط وقتی می‌سازی که `expired` را خودت تشخیص بدهی | خریدار دوباره پول می‌دهد و دو فاکتور باز و دو بار کسر از کیف پول داری |

پیام «نتیجه درخواست قبلی هنوز مشخص نیست» از سیبیل‌پی نیست. سیبیل‌پی هیچ‌وقت به‌خاطر یک فاکتور باز، درخواست بعدی را رد نمی‌کند.

## الگوی درست

قبل از ساخت فاکتور، از درگاه بپرس:

```http
GET /api/v1/invoices/by-order/{order_id}
```

| پاسخ استعلام | یعنی | کار درست |
|---|---|---|
| `pending` یا `partially_paid` | فاکتور هست و باز است | همان `payment_url` را دوباره بفرست و فاکتور تازه نساز |
| `paid` | قبلا پرداخت شده | سفارش را تحویل بده و دوباره پول نگیر |
| `404 NOT_FOUND` | ساخته نشده | فاکتور تازه بساز |
| `expired` یا `cancelled` | مرده است | با `order_id` جدید فاکتور بساز |

### Python

```python
async def get_or_create_payment(user, rial, cart):
    order_id = f"{cart.id}-{int(time.time())}"          # یکتا برای همین تلاش
    found = await sibil_get(f"/api/v1/invoices/by-order/{order_id}")   # ۳ خط
    if found is None or found["status"] in ("expired", "cancelled"):
        found = await sibil_post("/api/v1/invoices",
                                 {"amount_rial": rial, "order_id": order_id})
    return found["payment_url"], found["payable_rial"]
```

### PHP

```php
$order_id = $cart->id . '-' . time();
$r = sibil_call('GET', "/api/v1/invoices/by-order/$order_id");
if (!$r || in_array($r['status'], ['expired', 'cancelled'], true)) {
    $r = sibil_call('POST', '/api/v1/invoices',
        ['amount_rial' => $rial, 'order_id' => $order_id]);
}
header('Location: ' . $r['payment_url']);
```

### Node.js

```js
const orderId = `${cart.id}-${Date.now()}`;
let inv = await sibil('GET', `/api/v1/invoices/by-order/${orderId}`);
if (!inv || ['expired', 'cancelled'].includes(inv.status)) {
  inv = await sibil('POST', '/api/v1/invoices', { amount_rial: rial, order_id: orderId });
}
return { url: inv.payment_url, payableRial: inv.payable_rial };
```

دو قاعده تکمیلی:

1. `pending` را با استعلام حل کن، نه با قفل. هر چند دقیقه یک‌بار `by-order` بزن یا webhook بگیر و قفل کاربر را بردار.
2. `expired` را خودت تشخیص بده. `expires_at` را ذخیره کن؛ اگر گذشته و وضعیت هنوز `pending` بود، قبل از پیام «منتظر بررسی» یک‌بار استعلام بزن.

## اتصال به افزونه‌های آماده

ربات‌های فروش آماده معمولا «یک پرداخت معلق برای هر کاربر» را در دیتابیس خودشان نگه می‌دارند و به‌جای استعلام تا ابد صبر می‌کنند. برای سازگار کردنشان سه خط کافی است، دقیقا جای همان قفل:

```python
# قبل از «قفل کردنِ» کاربر:
inv = await sibil_get(f"/api/v1/invoices/by-order/{order_id}")
if inv and inv["status"] == "pending":
    return inv["payment_url"]     # همان لینک را بده، قفل نکن
if not inv or inv["status"] in ("expired", "cancelled"):
    inv = await sibil_post("/api/v1/invoices", {"amount_rial": rial,
                                                "order_id": order_id})
```

اگر افزونه کد بسته دارد و قابل تغییر نیست، در تنظیماتش `order_id` را از «شناسه کاربر» به «شناسه سفارش + زمان» تغییر بده. همین یک کار صف را می‌شکند.

## چک‌لیست قبل از انتشار

- [ ] هر تلاش خرید `order_id` یکتا دارد (`cart-id + timestamp` یا UUID).
- [ ] قبل از ساخت فاکتور `by-order` زده می‌شود و جواب `pending` یعنی همان لینک.
- [ ] `payable_rial` بدون گرد کردن به مشتری نشان داده می‌شود، هم ریال هم تومان.
- [ ] `status: paid` را از webhook یا `GET .../status` می‌گیری، نه از صفحه بازگشت.
- [ ] تحویل سفارش idempotent است؛ دو بار `paid` یعنی یک تحویل.
- [ ] هیچ‌جای کد، فاکتور جدید کاربر را به فاکتور باز قبلی گره نمی‌زند مگر با همان `order_id`.
- [ ] رفتار در `AMOUNT_POOL_EXHAUSTED` مشخص است: پیام صادقانه و تلاش دوباره کوتاه.
