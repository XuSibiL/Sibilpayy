# ۱۸ — وصل‌کردنِ یک بات به وب‌هوکِ چندمقصدی

> **مسئله‌ای که این سند جواب می‌دهد:** یک ربات (مثلاً «میرزا» یا «سیبیل‌پنل») فقط
> **کلیدِ API فروشگاه** و یک آدرسِ HTTPS دارد. چطور مقصدِ وب‌هوکِ **خودش** را ثبت
> کند، بدونِ توکنِ ادمین، بدونِ دست‌زدن به اتصالِ بات‌های دیگر، و طوری که هر فاکتور
> فقط به همان مقصدی برود که از آن ساخته شده؟

---

## ۰) دو نوعِ مسیر، دو نوعِ دسترسی

| مسیر | دسترسی | برای چه کسی |
|---|---|---|
| `/api/v1/admin/stores/{store}/webhooks` | `X-Admin-Token` | اپراتورِ پلتفرم (پنل ادمین) |
| `/api/v1/hooks/self` | `Authorization: Bearer <کلیدِ API همین فروشگاه>` | خودِ اتصال (بات، سایت، فروشگاه) |

مسیرهای ادمین دسترسی به **همهٔ** کلیدها و مقصدهای یک فروشگاه دارند. مسیرهای
`hooks/self` **فقط** روی مقصدهای همان کلیدی کار می‌کنند که توکنش را فرستاده؛ نه
کلیدِ دیگر، نه فروشگاهِ دیگر. اگر بخواهی به مقصدِ یک کلیدِ دیگر دست بزنی، پاسخ
`404 UNKNOWN_ENDPOINT` است — نه ۴۰۳، تا حتی وجودِ آن مقصد هم لو نرود.

---

## ۱) فهرستِ مقصدهای همین کلید

```http
GET /api/v1/hooks/self
Authorization: Bearer sp_live_…
```

```json
{"success": true, "data": {
  "key": "pk_ab12",
  "max": 3,
  "count": 1,
  "endpoints": [
    {"id": "ep1", "label": "mirza", "url": "https://mirza.example/hook",
     "enabled": true, "secret_masked": "whsec_afab…", "bound": true,
     "last": {"event": "invoice.paid", "status": "delivered", "code": 200,
              "attempts": 1, "at": "2026-11-17T12:40:11+00:00", "error": null}}
  ]
}}
```

`secret_masked` تنها شکلی است که secret در آن دیده می‌شود. `last` آخرین تحویلِ
همان آدرس است (`null` یعنی هنوز چیزی نرفته).

---

## ۲) ثبتِ مقصدِ خودش — بدونِ توکنِ ادمین، بدونِ تخریب

```http
PUT /api/v1/hooks/self
Content-Type: application/json

{"url": "https://mirza.example/hook", "label": "mirza"}
```

قواعدِ دقیق:

| حالت | رفتار |
|---|---|
| آدرس تازه، کمتر از سه مقصد | مقصد ساخته می‌شود؛ `created: true` و **secret کامل فقط در همین پاسخ** |
| همان آدرس دوباره | همان مقصد برمی‌گردد؛ `created: false`، **نه مقصدِ تکراری، نه secretِ تازه** |
| `{"id": "ep2", "url": "…"}` | آدرسِ همان مقصد عوض می‌شود؛ secret دست‌نخورده (`secret_unchanged: true`) |
| سه مقصد پر است و آدرسِ چهارم | `409 LIMIT_REACHED` — هیچ مقصدی خودکار حذف نمی‌شود |
| `{"id": "ep9"}` که مالِ این کلید نیست | `404 UNKNOWN_ENDPOINT` |
| آدرسِ `http://` (غیرِ لوکال) | `400 INVALID_URL` |
| دو درخواستِ هم‌زمان | یک بار تکرارِ خودکار؛ اگر باز هم برخورد بود `409 CONCURRENT_UPDATE` — همان درخواست را دوباره بفرست |

پاسخِ ساخت:

```json
{"success": true, "data": {
  "created": true, "id": "ep1", "url": "https://mirza.example/hook",
  "secret": "whsec_afab5b7561b673caa07e300117597c24b7caeac4720529f3",
  "secret_note": "این secret دیگر نمایش داده نمی‌شود؛ گم شد → rotate",
  "count": 1, "max": 3
}}
```

نکتهٔ مهم: این مسیر **هیچ‌وقت کلِ فهرست را جایگزین نمی‌کند**. `PUT` روی مسیرهای
ادمین «همه را با این فهرست عوض کن» است؛ اینجا `PUT` یعنی «این یکی را بساز یا
پیدا کن». پس باتِ تازه نمی‌تواند اتصالِ باتِ دیگر را پاک کند.

---

## ۳) کدام مقصد برای کدام فاکتور

هنگامِ ساختِ فاکتور، مقصد به این ترتیب انتخاب و **روی خودِ فاکتور ثبت** می‌شود:

1. اگر بدنهٔ فاکتور فیلدِ `webhook_endpoint` را داشته باشد و آن مقصد **متعلق به همان
   کلید** باشد → همان.
2. وگرنه اولین مقصدِ همان کلید.
3. فاکتورهای قدیمی که این فیلد را ندارند → اولین مقصدِ فروشگاه (رفتارِ قبلی، بدونِ
   قطعی).

```http
POST /api/v1/invoices
Authorization: Bearer sp_live_…
Content-Type: application/json

{
  "amount_rial": 500000,
  "order_id": "ORD-1001",
  "webhook_endpoint": "ep2"
}
```

* `webhook_endpoint` **اختیاری** است؛ بقیهٔ بدنه همان قبلی است و چیزی اجباری نشده.
* مقصدِ نامعتبر → `400 UNKNOWN_ENDPOINT` (فاکتور ساخته نمی‌شود).
* هنگامِ تأییدِ پرداخت، فقط همان یک آدرس فراخوانی می‌شود؛ با secretِ همان مقصد.
* اگر کلید عوض شود یا مقصد پاک شود، فاکتورهای قبلی همان مقصدی که ثبت کرده‌اند را
  نگه می‌دارند؛ اگر آن مقصد دیگر وجود نداشته باشد، به اولین مقصدِ فروشگاه برمی‌گردد.

## ۴) امضای وب‌هوک — یک قاعده، نه دو تا

هدر:

```
X-SIBILPAY-Signature: t=1763380800,v1=e3ad64aa…
X-SIBILPAY-Event: invoice.paid
X-SIBILPAY-Delivery: whd_…
```

قاعده:

```
string_to_sign = f"{t}." + raw_body
v1             = HMAC_SHA256(secret_of_that_endpoint, string_to_sign).hexdigest()
```

* `secret` همان مقصدی است که پیام به آن می‌رود (`whsec…`)، نه secretِ فروشگاه.
* `raw_body` **بایت‌های خامِ بدنه** است، پیش از هر پارس/بازچینش. اگر بدنه را
  دوباره `json.dumps` کنی، امضا نمی‌خواند.
* محافظت از بازپخش: `t` را با ساعتِ خودت مقایسه کن؛ اختلافِ بیش از ۳۰۰ ثانیه را رد
  کن. `X-SIBILPAY-Delivery` را هم برای حذفِ تکراری نگه دار (تحویلِ دوباره همان
  شناسه را دارد).

نمونهٔ تست (secret آزمایشی، بدونِ هیچ مقدارِ واقعی):

```
secret = "whsec_test_123"
body   = {"event":"invoice.paid","data":{"id":"inv_9001","status":"paid"}}
t      = 1763380800
v1     = e3ad64aa1f8e55a9db83cce8862ada3804abf7d8ee64d2a25bbd3f26c532bfd2
header = t=1763380800,v1=e3ad64aa1f8e55a9db83cce8862ada3804abf7d8ee64d2a25bbd3f26c532bfd2
```

```python
import hmac, hashlib
expected = hmac.new(secret.encode(), f"{t}.".encode() + raw_body, hashlib.sha256).hexdigest()
assert hmac.compare_digest(expected, v1)
```

## ۵) گرفتنِ secret و چرخشِ آن

* secret **فقط یک بار** برمی‌گردد: در پاسخِ ساخت (`PUT`) و در پاسخِ چرخش.
* `GET` همیشه `secret_masked` می‌دهد؛ راهی برای خواندنِ دوبارهٔ secretِ کهنه نیست.
* اگر پاسخِ ساخت وسطِ راه قطع شد و secret را نگرفتی:

```http
POST /api/v1/hooks/self/rotate
{"id": "ep1"}
```

```json
{"success": true, "data": {"id": "ep1", "url": "https://mirza.example/hook",
  "secret": "whsec_a85b7323…", "note": "فقط همین یک بار نمایش داده می‌شود"}}
```

بعد از چرخش، امضاهای قبلی معتبر نیستند؛ مقصد همان است و آدرس عوض نمی‌شود.
secretِ مقصدهای دیگر هرگز در این پاسخ‌ها نمی‌آید.

## ۷) رواداریِ ۱۰ ریالی — کجا هست و کجا نیست

رواداری **فقط در تطبیقِ واریزی** (پیامکِ بانک → فاکتور) اعمال می‌شود، چون بانک
مبلغ را به تومان گِرد می‌کند. روی وضعیت `paid` و پاسخ‌های `GET`/`verify` هیچ
محاسبهٔ تازه‌ای انجام نمی‌شود؛ آن‌ها فقط واقعیتِ ثبت‌شده را برمی‌گردانند.

نمونه: فاکتور با `amount_rial = 300000`، `payable_rial = 300075`، واریزیِ
`300070` (۵ ریال کم، چون بانک گِرد کرده):

| فراخوانی | نتیجه |
|---|---|
| `GET /api/v1/invoices/{id}` | `status: "paid"`, `payable_rial: 300075`, `paid_amount_rial: 300070` |
| `GET /api/v1/invoices/{id}/status` | `paid` |
| `POST /api/v1/invoices/{id}/verify` | `{"verified": true, "verified_at": "…", "receipt_token": "…"}` |

**مبنای «مبلغِ وصول‌شده» = `paid_amount_rial`**؛ مبنای «طلبِ سفارش» = `amount_rial`.
`payable_rial` فقط مبلغِ دقیقِ قابلِ پرداخت (با دنبالهٔ یکتا) است و مبنای حسابداری
نیست. ۱۰ ریال رواداری مجوزِ نادیده‌گرفتنِ کسریِ واقعی نیست: اگر واریزی بیش از ۱۰
ریال کم باشد، فاکتور `partial` می‌شود و در «نیازمند بررسی» می‌ماند.

## ۸) `WALLET_INSUFFICIENT` — کِی برمی‌گردد و چه چیزی را خراب می‌کند

این خطا **فقط در ساختِ فاکتور** برمی‌گردد (نگهبانِ کیفِ کارمزد)، نه در پرداخت:

| عملیات | رفتار |
|---|---|
| `POST /api/v1/invoices` با کیفِ خالی | `402 WALLET_INSUFFICIENT`؛ فاکتوری ساخته نمی‌شود، پس واریزیِ گم‌شده هم در کار نیست |
| مشتری واریز کرده و کیف خالی است | فاکتور `paid` می‌ماند؛ کارمزد به‌صورتِ منفی روی کیف ثبت می‌شود و **پرداخت هرگز به‌خاطرِ کیفِ خالی از دست نمی‌رود** |
| وب‌هوکِ `invoice.paid` | ارسال می‌شود؛ کیفِ کارمزد به آن کاری ندارد |
| `POST /verify` | مستقل از کیف کار می‌کند |
| بعد از شارژِ کیف | هیچ «بازیابیِ» لازم نیست؛ فاکتورهای قدیمی سرِ جایشان‌اند و فاکتورِ تازه ساخته می‌شود — مشتری لازم نیست دوباره پرداخت کند |

پیامِ این خطا برای مشتری عمداً کلی است («درگاه موقتاً در دسترس نیست»)؛ دلیلِ واقعی
با یک اعلانِ یک‌باره به فروشنده می‌رسد.

---

## ۹) چک‌لیستِ اتصالِ یک باتِ تازه

1. `GET /api/v1/hooks/self` — ببین از سه مقصد چند تا پر است.
2. `PUT /api/v1/hooks/self` با آدرسِ HTTPSِ خودت — secret را همان‌جا ذخیره کن.
3. `POST /api/v1/hooks/self/test` — تحویل را در `/deliveries` ببین.
4. در ساختِ فاکتور اگر لازم شد `webhook_endpoint` را بده؛ وگرنه مقصدِ همین کلید
   خودکار انتخاب می‌شود.
5. امضا را با `t.<body>` و secretِ همان مقصد چک کن؛ بیشتر از ۳۰۰ ثانیه را رد کن.
